## 0. 一句话目标

在酒馆战棋对局中，从 `Power.log` 实时还原盘面 → 规则引擎算出硬指标 → 由 **JevK5** 模型对模糊局势做判断题 → 在**不干扰游戏**的前提下给出可执行的建议。

---

## 1. 背景与动机

### 1.1 为什么可行（已实测）

炉石在 macOS 上把完整对局状态写入纯文本日志，本机确认：

| 事实 | 实测值 |
|---|---|
| 日志根目录 | `/Applications/Hearthstone/Logs/` |
| 会话目录数 | 6 个 |
| 最新 `Power.log` | `/Applications/Hearthstone/Logs/Hearthstone_2026_10_10_21_11_09/Power.log`，**92 MB** |
| 次新 `Power.log` | `/Applications/Hearthstone/Logs/Hearthstone_2026_10_09_20_49_31/Power.log`，**100 MB** |
| `BACON_` 相关行 | **55,974** 行 |
| `TB_BaconShop` 标识 | **53,204** 次 |
| 战棋专用 tag | **81 种** |
| `CREATE_GAME` 对局数 | 4（该文件） |
| 行格式 | `D HH:MM:SS.fffffff GameState.DebugPrintPower() - <载荷>` |
| 日志分类 | `GameState.` **344,567** 行、`PowerTaskList` **334,597** 行、`Bacon` **55,974** 行 |

**关键结论**：日志里有**足够重建盘面的信息**，且是**明文文本**，无需注入、无需读内存、无需抓包。

### 1.2 现有配置状况

| 项 | 状态 |
|---|---|
| `/Applications/Hearthstone/log.config` | ❌ **不存在**（Power 日志按默认级别全量输出） |
| `client.config` | `[Log]` / `FileSizeLimit.Int=-1` |
| 后果 | ⚠️ **日志不轮转、无限增长**，单次会话 90–100 MB，需自行处理体积与历史清理 |
| `Gameplay.log` | 仅 UI 报错（`Unable to display tooltips from actor ...`），**与战棋无关** |

### 1.3 与既有方案的关系

- [Lanternko/jev-hearthstone](https://github.com/Lanternko/jev-hearthstone)：读 `Power.log` 判盘面 → 规则/搜索剪枝 → **Jev** 选一步 → **模拟鼠标点出**。**标准模式**（含弃牌术打法），**不是酒馆战棋**。
- 本项目差异：① 目标是**战棋**；② 只做**提示**，**不点鼠标**；③ 模型用**本地开源的 JevK5**。

## 2. 目标与非目标

### 2.1 目标（In Scope）

| # | 目标 | 验收信号 |
|---|---|---|
| G1 | 实时读日志，稳定还原当前盘面 | 任意时刻能打印出结构完整、数值正确的 state |
| G2 | 覆盖一局完整生命周期 | 选英雄 → 每回合 → 战斗 → 结算排名，全程无崩溃 |
| G3 | 输出**可执行**的建议 | 建议是"买下第 2 张/升本到 5/卖 X"这种能直接照做的形式 |
| G4 | 建议**不拖后腿** | 建议出现延迟 ≤ 1.5 s，不遮挡关键 UI |
| G5 | 模型可替换 | JevK5 换成别的 provider 只改配置，不改业务代码 |
| G6 | 对局可回放/复盘 | 每局落盘为结构化 JSON，可离线重看 |

### 2.2 非目标（Out of Scope）

| # | 不做 | 理由 |
|---|---|---|
| N1 | ❌ **不模拟鼠标/键盘操作游戏** | 用户明确只要**辅助提示**；自动化有封号风险 |
| N2 | ❌ 不全自动进入下一局 | 同上 |
| N3 | ❌ 不修改游戏文件、不读进程内存 | `Power.log` 已够用，越界手段风险高 |
| N4 | ❌ 不做标准模式/竞技场 | 本期只战棋 |
| N5 | ❌ 不做云端账号体系 | 纯本地，无联网需求（除模型下载） |
| N6 | ❌ 不做对手牌库预测（"猜牌"） | 战棋无固定牌库推理，收益低、噪声大 |
| N7 | ❌ **不做双人（Duos）模式** | ✅ 用户决策（m00926）：**只做单人** |

### 2.3 一条硬约束

> ⚠️ **本工具只能"看"不能"动"**。任何建议都由人确认后手动操作。这条是**红线**，架构上不给执行层留接口。

## 3. 用户与场景

### 3.1 用户画像

- **主用户**：本机使用者（Mac mini M4），战棋有基础、想提高决策质量的中高阶玩家。
- 特征：知道机制，缺的是"这一手该不该贪"的判断和**实时数值**（升本期望、三连概率、对手威胁）。

### 3.2 核心场景

| 场景 | 时机 | 期望 |
|---|---|---|
| S1 选英雄 | 开局三选一 | 给出每个英雄的强弱倾向 + 推荐（✅ 实证分见 §11.17） |
| S2 每回合商店 | 刷卡阶段 | "买哪张/该不该刷新/该升本吗" |
| S3 ~~摆位~~ | ~~战斗前~~ | ❌ **已移出范围**（用户决策 m00926：**无需摆位提示**） |
| S4 血线预警 | 任意时刻 | "你还有 X 血，本轮伤害上限 Y，危险" |
| S5 饰品/发现选择 | 触发时 | 多选项打分排序 |
| S6 赛后复盘 | 对局结束 | 回放每回合决策与当时建议 |

## 4. 功能需求

整体流水线（**四层解耦**，见 §7）：

```
Power.log ──► ①采集 ──► ②状态解析 ──► ③规则引擎 ──► ④JevK5 顾问 ──► 提示 UI
   (tail)      (增量)      (state)       (硬指标)      (判断题)       (展示)
```

### FR-1 日志采集层

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-1.1 | 自动发现最新会话目录 | 扫 `Logs/`，按 `Hearthstone_YYYY_MM_DD_HH_MM_SS` 取最新 |
| FR-1.2 | 增量 tail | 记录 offset，只读新增字节，**不重读 92 MB** |
| FR-1.3 | 处理日志轮换/游戏重启 | 游戏重启会新建会话目录，需检测并切换，重置游戏状态 |
| FR-1.4 | 检测对局边界 | 以 `CREATE_GAME` 开头、`GameEntity` 的 `PLAYSTATE` 结束为一局 |
| FR-1.5 | 体积控制 | 单文件 100 MB 级，禁止整文件读入内存；顺序流式解析 |
| FR-1.6 | 断点续读 | 程序重启后能从上次 offset 继续 |

> ✅ FR-1 可行性已由实测确认（无非 UTF-8 字节风险未验证，见 风险 R4）。

### FR-2 状态解析层

**输出物**：一个 `GameState` 结构（JSON），至少包含：

| 字段 | 来源（已实测的 tag / 标记） |
|---|---|
| 玩家列表（8 人） | `tag=CARDTYPE value=PLAYER`、`tag=PLAYER_ID`、`tag=HERO_ENTITY` |
| 玩家名（中文） | ❗ `PowerTaskList` 分支的 `Entity=调酒师鲍勃` / `Entity=测试玩家#1234` 形态 |
| 英雄 | `FULL_ENTITY - Creating ID=73 CardID=TB_BaconShop_HERO_KelThuzad` |
| 鲍勃（酒馆） | `CardID=TB_BaconShopBob` |
| 随从身材 | `tag=ATK`（13,012 次）、`tag=HEALTH`（13,048）、`tag=DAMAGE`（2,492） |
| 随从位置 | `tag=ZONE_POSITION`（11,084） |
| 归属 | `tag=CONTROLLER`（18,786） |
| 区域 | `tag=ZONE`（39,250，主事件源） |
| 科技等级 | `tag=TECH_LEVEL`（10,326） |
| 金币 | `tag=RESOURCES`（158）、`tag=RESOURCES_USED`（460） |
| 回合数 | `TAG_CHANGE Entity=GameEntity tag=TURN value=N` |
| 回合阶段 | `tag=STEP`：`BEGIN_MULLIGAN` / `MAIN_READY` / `MAIN_START_TRIGGERS` / `MAIN_END` / `MAIN_CLEANUP` / `MAIN_NEXT` |
| 当前行动方 | `tag=CURRENT_PLAYER value=1`（196 次） |
| 战斗阶段 | `tag=BACON_IN_COMBAT_PHASE`（92）、`tag=BACON_CURRENT_COMBAT_PLAYER_ID`（184） |
| 三连候选 | `tag=BACON_TRIPLE_CANDIDATE`（18）、`tag=BACON_PAIR_CANDIDATE`（134）、`tag=BACON_TRIPLE_UPGRADE_MINION_ID`（8,410） |
| 关键词 | `DIVINE_SHIELD`(782)、`TAUNT`(538)、`REBORN`(1024)、`WINDFURY`(204)、`STEALTH`(140)、`FROZEN`(334)、`VENOMOUS`(28) |
| 饰品 | `tag=CARDTYPE value=BATTLEGROUND_TRINKET`、`CardID=BG30_Trinket_1st` / `BG30_Trinket_2nd`、`tag=BACON_TRINKET`(280)、`tag=BACON_TRINKETS_ACTIVE`(4) |
| 对手威胁 | `tag=BACON_COMBAT_DAMAGE_CAP`(16)、`tag=BACON_DAMAGE_CAP_ENABLED`、`tag=BACON_DIED_LAST_COMBAT`(262)、`tag=BACON_WON_LAST_COMBAT`(100) |

| 编号 | 需求 |
|---|---|
| FR-2.1 | 解析 `FULL_ENTITY` / `SHOW_ENTITY` / `TAG_CHANGE` / `CHANGE_ENTITY` 四类事件 |
| FR-2.2 | 维护实体表（EntityID → 属性），`TAG_CHANGE` 做增量更新 |
| FR-2.3 | ⚠️ **`tag=NAME` 实测出现 0 次** —— 日志**只有 CardID，没有卡牌名**，必须外挂卡牌数据做 `CardID → 中文名` 映射 |
| FR-2.4 | 处理 `PowerTaskList` 与 `GameState` **两份重复输出**（各约 34 万行）：**只取一份**，否则事件翻倍 |
| FR-2.5 | 正确处理 `BlockType=TRIGGER/POWER/PLAY/ATTACK/DEATHS/MOVE_MINION` 的嵌套 |
| FR-2.6 | 只在自己回合/关键节点产出快照，避免每行都触发模型调用 |

> ⚠️ **FR-2.4 是易踩的坑**：同一动作在 `GameState.DebugPrintPower()` 和 `PowerTaskList.DebugPrintPower()` 各打一遍，不去重会导致状态错乱或重复计数（实测两者行数几乎相等：344,567 vs 334,597）。

### FR-4 规则引擎层（硬指标，**不依赖任何模型**）

> 设计原则：**能用规则算的绝不用模型**。模型只处理无法量化的判断题。

| 编号 | 建议项 | 计算方式 |
|---|---|---|
| FR-4.1 | 升本期望/性价比 | 当前等级 → 下一级费用、当前回合数、剩余金币 |
| FR-4.2 | 三连/对子状态 | 统计自家随从的 CardID 重复度，标出"再 1 张即三连" |
| FR-4.3 | 血线与生存 | 当前血量、`BACON_COMBAT_DAMAGE_CAP`、上轮是否败 (`BACON_DIED_LAST_COMBAT`) |
| FR-4.4 | 场面强度评估 | 自家随从总身材/关键词评分 vs 对手已知信息 |
| FR-4.5 | 族群/流派统计 | `BACON_SUBSET_*` 标签族（野兽 2020、龙 1114、海盗 856、亡灵 842、元素 650、恶魔 436、机械 310、鱼人 186、娜迦 86、野猪人 8）用于判断"这条线还能不能走" |
| FR-4.6 | 刷新与冻结价值 | `BACON_FREE_REFRESH_COUNT`(36)、`BACON_NUM_MAX_REROLL_PER_HERO`(4)、`BACON_SELL_VALUE`(18) |
| FR-4.7 | 饰品/发现候选打分 | 基于 `BACON_IS_POTENTIAL_TRINKET`、`BACON_TURNS_LEFT_TO_DISCOVER_TRINKET` |

**要求**：FR-4 全部可**离线单测**（喂历史日志 → 断言指标）。这是质量地基，必须先于模型完成。

### FR-5 模型顾问层（JevK5）

#### FR-5.1 接口形态（已实测确认的 API）

JevK5 是 [allebee/jevk5](https://github.com/allebee/jevk5)（**Apache-2.0**，与 TypeSafe 无关），本地服务端接受 TypeSafe 风格请求：

```bash
jevk5-serve --model alibiserikbay/JevK5 --port 8090
```

```json
POST /v1/systemone
{
  "state": "<状态文本>",
  "questions": {
    "q1": {
      "type": "choice",
      "instructions": "<问题>",
      "criteria": ["选项A", "选项B", "选项C"]
    }
  }
}
```

支持三种题型：**`noul`**（是/否，返回 `true` 概率）、**`choice`**（多选一，返回每个选项概率）、**`score`**（分档打分）。

Python 直调：

```python
from jevk5 import JevK5
model = JevK5("alibiserikbay/JevK5")          # v0.3, ~9 GB GPU 显存 bf16
model.decide("...state...", {"type": "noul", "instructions": "..."})
# {'type': 'noul', 'confidence': ..., 'noul': <p(true)>, 'input_tokens': ...}
```

#### FR-5.2 ⚠️ 必须正视的 JevK5 限制（决定架构）

| 限制 | 实测/文档事实 | 对本项目的影响 |
|---|---|---|
| **只支持英文** | README: "The model is English-only" | ❗**最大阻塞**。中文盘面（英雄名/卡名）需**翻译或直接以英文 CardID/英文名喂入**。→ 见 ADR-4 |
| **不生成自由文本** | 一次前向输出**选项字母的 softmax**，"zero generated tokens" | **不能输出数字**。所有数值（升本期望、伤害）必须由 FR-4 规则算好，作为 `state` 文本的一部分 |
| **选项上限 16/趟** | 超过 16 个选项需 `ceil(n/16)+1` 趟组合 | 战棋"发现"常 >16 项，会用多趟，延迟上升 |
| **输入上限 16,384 token** | 超长直接**拒答** | state 必须精简，不能整段日志喂进去 |
| **单卡串行** | server 在单 GPU 上串行处理请求 | 并行的多个问题要排队，实时性受影响 |
| **量化损失** | Q4_K_M 在 231 公开题上比 bf16 少 10 题一致（221/231） | 若跑量化版，准确性下降可接受但需知情 |

#### FR-5.3 本机可用的部署形态（16 GB M4）

| 形态 | 体积 | 速度（文档实测） | 评价 |
|---|---|---|---|
| `jevk5-4b-v0.3-Q4_K_M.gguf` | **2.71 GB** | M1 Pro 上 4B 约 **0.6 s/决策**（CPU） | ✅ **本机首选** |
| `jevk5-4b-v0.3-Q8_0.gguf` | 4.48 GB | 同上，略慢 | 质量更高，内存仍可接受 |
| `jevk5-4b-v0.3-Q5_K_M.gguf` | 3.07 GB | 折中 | 备选 |
| `JevK5-9B` 系列 | ≥ 6.47 GB | 更慢 | ⚠️ 16 GB 机器风险高，且 hard tier **反而更差**（0.730 vs 4B 的 0.784） |
| `JevK5-Lite`（437M DeBERTa） | 很小 | CPU 71–205 ms | ⚠️ 实验性，hard tier 仅 0.405，**不建议主力** |
| bf16 全量（`JevK5`） | ~9 GB 显存 | H100 13 ms | ❌ 本机无 CUDA，不适用 |

> **注意**：9B 在 JevBench **公开题**上不如 4B（0.730 vs 0.784），且 hard-tier 校准更差（ECE 0.126 vs 0.054）。**不要因为"更大"就选 9B**。

#### FR-5.4 功能需求

| 编号 | 需求 |
|---|---|
| FR-5.4.1 | **provider 抽象层**：JevK5 只是其中一种实现，支持切换（`jevk5` / `llamacpp` / OpenAI 兼容 / 未来真 Jev） |
| FR-5.4.2 | 题型适配：把每个建议点映射成 `noul` / `choice` / `score` |
| FR-5.4.3 | **置信度门控**：低置信度不显示建议（宁可不给，也别乱给） |
| FR-5.4.4 | **超时保护**：模型超时/拒答时优雅降级到 FR-4 规则建议 |
| FR-5.4.5 | **提示词模板可配置**，便于针对战棋调优 |
| FR-5.4.6 | 控制 `state` token 数（目标 < 2,000），规避 16,384 上限 |
| FR-5.4.7 | 记录每次调用的延迟、token、置信度，用于评估 |

### FR-6 展示层（UI）

#### FR-6.0 技术要点（已调研）

| 项 | 方案 | 说明 |
|---|---|---|
| 取炉石窗口位置/尺寸 | **Accessibility API**（`AXUIElement`，`kAXPositionAttribute` / `kAXSizeAttribute`） | ⚠️ 需要用户授予**辅助功能权限**（AXIsProcessTrusted），且**不能用终端输入**——这是浏览器/终端类工具不可行的原因 |
| 监听窗口变化 | `AXObserver` 监听 `kAXWindowMovedNotification` / `kAXWindowResizedNotification` | 比轮询省电；兜底可用 200 ms 定时轮询 |
| 无权限降级 | 走**固定位置**模式（用户手填窗口矩形）或纯屏幕右缘吸附 | 不让权限缺失直接导致功能不可用 |
| 置顶 | `NSWindow.level = .floating` | 压在游戏之上但**不抢焦点** |
| 不抢焦点 | `NSWindow` 用 **非激活面板**（`NSPanel` + `becomesKeyOnlyIfNeeded`，或 `styleMask` 去掉 `titled`） | 点悬浮框不能打断游戏操作 |
| 全屏兼容 | `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary]` | ⚠️  macOS 全屏会把游戏放进**独立 Space**，漏了这两项悬浮框会直接消失 |
| 点击穿透（可选） | `ignoresMouseEvents = true` | 吸附在窗口**外侧**时非必需；若与游戏重叠则必须开 |
| 宽度 | 建议 **320–360 pt** | 本机实测：屏幕逻辑 **1920×1080**（4K @2x），炉石窗口化时右侧余量约 **640–1160 pt**，够用 |
| 构建 | 复用 `auxac-mac/build.sh` 模式 | ⚠️ 该脚本已探明：本机 DSH 沙箱下 **SwiftPM 不可用**（嵌套 sandbox 被拒），须用 `swiftc` 手搓 + `.app` 外壳（`MenuBarExtra` 依赖 bundle 标识） |

## 7. 架构决策（ADR）

| # | 决策 | 备选 | 理由 |
|---|---|---|---|
| ADR-1 | **四层解耦**（采集/解析/规则/模型） | 单体脚本 | 解析与规则要能做历史回归测试；模型层要能替换 |
| ADR-2 | **规则优先，模型兜底** | 全部交给模型 | JevK5 不能出数字；且战棋大量决策可精确计算，模型反而更慢更不稳 |
| ADR-3 | 先做 **CLI 验证流水线**，UI 后置 | 直接做 UI | 逻辑未验证时做 UI 是浪费 |
| ADR-4 | 盘面统一转**英文**喂 JevK5 | 中文直喂 | 模型明确声明 English-only |
| ADR-5 | 模型默认 **4B Q4_K_M** | 9B / Lite / bf16 | 见 FR-5.3：16 GB 友好，且公开题上 4B 优于 9B |
| ADR-6 | 用 **Swift/SwiftUI 原生悬浮框**，吸附炉石窗口右侧 | 本地网页 / 终端 UI | ✅ 用户决策（m00101）；右侧吸附要求**低延迟跟随窗口**，网页做不到；复用 `auxac-mac` 工程经验 |
| ADR-7 | 只解析 `GameState.DebugPrintPower()` 一份 | 两份都解析 | 避免事件重复（FR-2.4） |
| ADR-8 | 窗口几何用 **Accessibility API**（AXUIElement + AXObserver） | 定时轮询 `CGWindowListCopyWindowInfo` | 事件驱动、延迟低（FR-6.0.2 要求 ≤200 ms）；代价是需辅助功能权限，故 FR-6.0 保留无权限降级路径 |
| ADR-9 | 悬浮框用 **非激活 NSPanel + `.floating` + `.canJoinAllSpaces/.fullScreenAuxiliary`** | 普通 NSWindow | 不抢游戏焦点；且 macOS 全屏下游戏在独立 Space，缺这两项会直接不可见 |

> **ADR-6/8/9 由需求「吸附在炉石右边」直接推导**，原 ADR-6 的"UI 形态待定"已关闭。

**P0 期间新发现的三条日志规则（P1 必须遵守）**：

1. **命令词可以带缩进**：`TAG_CHANGE` 大量带前导空白（实测缩进 4:80,788 / 8:44,771 /
   12:7,300 / 16:4,182 / 20:1,295）。用 `re.match("^TAG_CHANGE")` 锚行首会**少一个数量级**
   （6,999 vs 146,027）。必须 `search()`。
2. **块内裸 `tag=` 行无实体前缀**：形态 `            tag=CONTROLLER value=14`，实测
   115,019 行。**归属规则**：缩进 k 的裸 tag 行属于 **`k − 4` 深度上最近声明的实体**
   （`self._entity_by_indent`）。漏掉这批会让 P1 漏掉随从进场/三连合成。
3. ⚠️ **`BLOCK_START` 的 `Entity=` 是"谁触发了这个块"，不是"属性属于谁"**：块内的
   `FULL_ENTITY` 属于它自己，不属于触发者。`BLOCK_START` **不能**登记进深度归属表，
   否则 766 条 `ATTACHED_TAG` 归属全错（已由 `tools/verify_attr_rule.py` 的语义自证锁住）。
4. `CREATE_GAME` 块的实体声明形如 `GameEntity EntityID=16` / `Player EntityID=17 PlayerID=6 ...`
   （声明缩进 4、属性缩进 8），每局 6 行（GameEntity 2 + Player 4），是
   `PLAYER_ID`/`HERO_ENTITY`/`BACON_MAX_PLAYER_TECH_LEVEL` 的唯一来源，
   连带的属性行共 352 行。
5. ⚠️ **`tag=HERO_ENTITY` 不是身份自证**：它写的是"这个玩家的英雄是谁"
   （实测 `Player EntityID=17` 的属性里 `tag=HERO_ENTITY value=35`）。只有
   `tag=ENTITY_ID` 能自证宿主身份——早期把 `HERO_ENTITY` 也当成宿主 id，
   立刻产生 4 条不一致（17≠35、18≠74、23≠39、24≠86）。
6. ⚠️ **`CREATE_GAME` 自身不登记缩进锚点**：它不带任何属性，紧跟其后、缩进 +4 的
   那批行是 GameEntity / Player 的**声明**。若在这里登记锚点，声明整行会被
   `_pending` 吸收分支吞掉，`PLAYER_ID` 全丢。

### P4 模型顾问层（`src/hsbg/provider.py` + `advisor.py` + `model_server.py`）

**本机模型**：用户下载的是 `jevk5-2b-v0.2-Q8_0.gguf`（2.01 GB，`arch=qwen35`）。

**关键结论：LM Studio 的 HTTP 服务不能用来跑 JevK5。**

| 端点 | 结果 |
|---|---|
| `/v1/completions` + `logprobs`/`n_probs` | `HTTP Error 400: Bad Request` |
| `/v1/completions` 不带 | `"logprobs": null` |
| `/v1/chat/completions` + `chat_template_kwargs.enable_thinking=false` | 参数不生效，100% token 记进 `reasoning_tokens` |

JevK5 的置信度全靠答案位置字母的 softmax，没有 logprob 就只能退化成生成式猜字母。
**出路**：LM Studio 自带 llama.cpp 引擎里的 `llama-server`（2.56.0）原生支持 `n_probs`。

**JevK5 协议要点（抄自官方 `jevk5/prompt.py`，Apache-2.0）**：
- system：`"Apply the supplied criterion to the supplied evidence. Choose exactly one listed option. Respond with only its uppercase letter, with no explanation or reasoning."`
- user：JSON `{"evidence", "criterion", "options":[{"letter","description"}]}`
- 模板：thinking off = **预填空 think 块** `<|im_start|>assistant\n<think>\n\n</think>\n\n`，
  答案位置的 token 就是选项字母
- 读法：**先 `/tokenize`（`parse_special:true`）再把 token id 喂 `/completion`**
  （`n_predict:1, n_probs:40, temperature:0`）→ 取 `completion_probabilities[0].top_logprobs`
- 概率 = `softmax(logprob / temperature)`，校准温度 **2B = 1.42**（v0.2 4B 1.532 / v0.3 4B 1.367 / 9B 1.089）
- 字母掉出 top-k 时用 `min(seen) - 2.0` 兜底（`MISSING_MARGIN`）

**⚠️ 教训：题面必须用官方 JSON 形状。** 我最早自创自然语言题面，4 题错 2 题
（"2/3 野兽该不该买"答 YES、"凑三连该不该买"答 NO）；换成官方形状后立刻合理。

**架构落地（ADR-2 规则优先、模型兜底）**：
- `advisor.build_evidence()` 把盘面翻成**英文**（ADR-4，JevK5 English-only），
  单测里有一条硬断言：evidence **不得含任何 CJK 字符**
- `advisor.build_questions()` 生成类型化提问：先 `choice`（只买一张买哪张），
  再 `noul`（要不要升本），再每张商店随从一个 `noul`（买不买）
- `advisor.consult()` 是总入口：模型不可用时**不抛异常**，返回
  `provider="rules-only"` + `note`，规则建议照常显示
- `model_server.py` 负责找 `llama-server`/GGUF 并启停服务（`./hsbg serve --start`）

**⚠️ 槽位编号的坑**：规则引擎的 `ShopItem.index` 是**游戏内槽位号**（刷新时按顺序建槽，
会越来越大），和盘面上 1..N 的显示序号不是一回事。直接给用户看"商店 #5"会让人去找
第 5 条，而商店只有 4 条。所以 `advisor.slot_label()` 统一翻成"哪张卡（商店第 N 项）"，
提问的 key 也用**槽位实体 id**（唯一）而不是只在一帧内唯一的序号。

```

**验收**：`./run-tests` **179 通过 0 失败**；`./hsbg check` **11/11**（44.4 MB/s）；

**已知局限（诚实记录）**：
- 本机只有 **2B** 档，区分度弱——上面那局 5 张随从的 `P(买)` 全在 0.43~0.46 之间，

- 超过 16 个选项时官方用 knockout 分趟；本项目暂不实现，超限时保留前 16 个并
  按比例扣掉被截断选项的份额（**不静默丢**）。

**下一阶段（P6 Swift 悬浮框）可用的原料**：`hsbg watch` 已能逐帧重绘；
`AdviceReport` 是可直接 JSON 化的结构；`advisor.consult()` 的返回包含
`report`（规则）、`answers`（模型）、`note`（降级说明）三块。

## 11.6 P6 实现状态与实测结论（2026-10-14）

**代码位置**：`native/FloatingPanel/`（Swift/AppKit 悬浮框）+ `src/hsbg/panel.py`（帧契约）
+ `src/hsbg/cli.py` 的 `panel` 子命令。P0–P4 与 P6 全部完成，`./run-tests` 182 通过、

### 11.6.1 端到端形态

```
Power.log → parser → StateBuilder → rules.RulesEngine → advisor(JevK5) → panel.PanelFrame
                                                                              ↓ JSON Lines
                                                          DataFeed(Swift) → FloatingPanel(NSPanel)
```

**为什么用子进程 + stdout 而不是 HTTP**：零端口、零鉴权、进程死掉立刻 EOF 可感知，
且 `./hsbg panel --json | head -1` 就是全部协议（ADP：面板与 Python 侧可各自独立调试）。

### 11.6.2 实测环境结论（改写 ADR-8）

| 项 | 实测 |
|---|---|
| `AXIsProcessTrusted()` | **false**；查自身 AX 返回 `-25208 = kAXErrorAPIDisabled` |
| `CGWindowListCopyWindowInfo` | **零权限可用**，拿到 14 个窗口的 owner 名 + 矩形 |
| 屏幕 | `frame=(0,0,1920,1080)`，`visibleFrame=(0,63,1920,987)`，`scale=2.0` |
| 炉石窗口（窗口化） | `1115×640`，右侧仅剩约 139 pt |

→ **ADR-8 修订**：**CGWindowList 为默认主路径**（`via=CGWindowList`），AX 仅用于提精度
（`via=AX`），都拿不到才退屏幕右缘（`via=屏幕右缘`）。比原方案更好：**用户无需开辅助功能**。
⚠️ `kCGWindowBounds` 左上原点 vs AppKit 左下原点，需 `flippedY = screenHeight - y - h`；
`kCGWindowName` 需屏幕录制权限而 owner 名不需要。

### 11.6.3 本轮修掉的 5 个真 bug（都是"看着像没数据、其实是接线错"）

| # | 位置 | 症状 | 根因 |
|---|---|---|---|
| 1 | `cli.py` `cmd_panel` | `--model-wait` 无效，永远拿不到模型意见 | 等待条件含 `runner.note`，而计算中它正是 `"模型思考中…"` → 第一轮就 break |
| 2 | `panel.py` / `advisor.py` | 模型答"商店第 2 项"却翻成另一张卡 | `report.shop` 按**分数**排序，而选项文本用**游戏槽位号**；两边口径不同 |
| 3 | `advisor.py` `consult()` | 同一帧带卡表与不带卡表问出**不同答案** | `ModelAdvisorRunner` 只传 `resolver` 不传 `db` → evidence 里是裸 CardID |
| 4 | `DataFeed.swift` | 面板永远只显示"等待炉石开局…" | 多传了 `--json`（`hsbg panel` 没这个开关）→ 退出码 2、无限重启 |
| 5 | `FloatingPanel.swift` | 面板跑到屏幕另一头（x=310） | "右侧放不下就翻到左边"；正确做法是**贴屏幕右缘**，仅在右缘也放不下时才翻左 |

**槽位编号最终口径（load-bearing）**：一律以 `slot_entity_id` 升序（= 炉石商店从左到右）。
`panel.build_frame()` 的 `display_index`、`advisor.pick_question()` 的选项文本、
`advisor._pick_shop_text()` 的翻回、`build_evidence()` 的 `shop slot N` **四处必须一致**，
否则模型看到的编号和界面上显示的编号会错位。

### 11.6.4 其余实现要点

- **答案翻译层**：模型只会返回英文选项原文（`"Buy the minion in shop slot 2"`），
  `advisor.question_text()` / `answer_text()` 负责翻成「现在升本？」「买「X」（商店第 N 项）」。

- **AppKit 的 `draw(at:)` 不裁剪** → `PanelContentView.clipToWidth()` 自己按字宽截断；
  商店行给右侧概率留 `reserveRight`，否则长卡名把 `P(买)` 挤到面板外。
- **调试开关** `HSBG_PANEL_FORCE_SHOW=1`：无视"炉石是否在前台"强制显示
  （默认炉石不在前台时 `alpha=0`，否则没法排查渲染）。
- **诊断日志** `/tmp/hsbgpanel.log`（`DataFeed.trace()`）：面板是 `LSUIElement` 后台 app，

### 11.7.1 卡文关键词（「发动」等）

**问题**：`mechanics` 字段**不覆盖**全部机制。实测 `BG36_099`（蚀脑怪）：

```
type=MINION  techLevel=2  attack=3
text='<b>发动（0）：</b>弃掉一张牌以使你的<b>神明</b>获得+2/+2。'
mechanics=None          ← 不是 ['发动']
```

全库 **50 张**（含金色版）带 `发动（N）` 的卡在 `mechanics` 上完全扫不到；
星级分布 1星2 / 2星8 / 3星12 / 4星18 / 5星6 / 6星4，
费用分布 0费10 / 1费26 / 2费14。

**实现**（`src/hsbg/rules.py`）：

| 新增 | 作用 |
|---|---|
| `parse_text_keywords(text)` | 从卡文模板抠关键词，返回 `["发动(0)"]` 这种带费用的键 |
| `_TEXT_KEYWORDS_WITH_COST = ("发动","复仇","塑造法术")` | **白名单** |
| `_TEXT_KEYWORDS = ("进击",)` | 无费用的关键词 |
| `_TEXT_TO_MECHANIC` | 中文词 → 英文 mechanics 标，用于去重 |
| `MECHANIC_WEIGHT` 扩充 | `发动(0)`1.6 / `发动(1)`1.2 / `发动(2)`0.9 / `BACON_RALLY`1.2 |
| `MECHANIC_ZH` | 中文标签（面板显示用） |
| `RulesEngine._mechanics()` | 合并 `mechanics` 字段与卡文关键词，带 `_mech_cache` |
| `RulesEngine._keyword_labels()` | 输出干净中文标签（`发动` 而不是 `发动(0)`） |
| `ShopItem.keywords` | 商店条目携带关键词，进 `reasons` 与面板帧 |

**两条踩过的坑（都写进 `docs/实现笔记.md`）：**

1. ⚠️ **白名单不可省**。宽松正则 `[\u4e00-\u9fff]{2,4}[（(]\d+[）)]` 会捞进
   **100 张无关卡**（`随从消耗(1)`、`出售获得(0)`、`铸币减少(2)` —— 异变/英雄技能/饰品）。
   加白名单后仍有 353 张卡命中，噪声卡（`BG27_Anomaly_721`、`BG23_HERO_305p`）归零。
2. ⚠️ **必须去重**。`BG21_001`（苍鳞鳄鱼）既有 `mechanics:['AVENGE','DEATHRATTLE']`
   又写了 `复仇（2）`，不去重就是 1.0 + 1.2 = 2.2 分。

## 11.8 饰品四选一 / 黑赐三选一接入（2026-10-15）

### 11.8.1 关键结构发现：选项不在 Power 流里

`GameState.DebugPrintEntityChoices()` 与 `GameState.SendChoices()` 是**唯一**的
选项来源，而 ADR-7 的"只解析 `DebugPrintPower` 一份"当初把它们排除了 ——
所以此前的实现在盘面上**完全看不到四选一**。这两条流只在 `GameState` 分支有，
`PowerTaskList` 无对应输出，加入 `DEFAULT_SOURCES` 不会导致事件翻倍。

一套机制覆盖四类场景（靠 `Source=` 区分）：

| 场景 | `ChoiceType` | `Source=` | 选项是什么 |
|---|---|---|---|
| 起手换牌 | `MULLIGAN` | `GameEntity` | 手牌（`zone=HAND`） |
| 黑暗之赐 | `GENERAL` | `cardId=BG36_MidGameEffect_010` | **随从**（挑谁吃赐福） |
| 小/大饰品 | `GENERAL` | `cardId=BG30_Trinket_1st` / `_2nd` | 饰品（`BATTLEGROUND_TRINKET`） |
| 卡牌效果发现 | `GENERAL` | 触发源卡（`三连奖励` / `死亡护命匣` / `无限潜力` / `猎头招聘`…） | 随从 |

### 11.8.2 三条 load-bearing 的日志规则

1. **`CountMin`/`CountMax` 是"选几个"不是"给了几个"**。实测每块 `CountMax=1`
   而选项 4/3/4/3 个（`{1: 4, 2: 3, 3: 4, 4: 3}`）。拿它判"收全"必然错。
2. **`Source=` 行与 `Entities[i]=` 行都不带 `id=`** → 只有头行能开新块。
   把 `Source=` 行也当"收尾上一个块"会让缓冲立刻变 None，后续选项全丢（实测真 bug）。
3. **选项逐行来，最后一行之后没有结束标记** → 只能"一有选项就把同一个对象挂上"
   （`_publish_choice`），靠规则层读 `state` 时拿到最新完整列表。

## 11.11 换成 4B 模型 + 悬浮框三个真机 bug（2026-10-15）

### 11.11.1 背景

用户下载完 `jevk5-4b-v0.2-Q4_K_M.gguf`（2.71 GB）。之前一直用

`P(买)` 全挤在 0.42~0.48，等于没给意见。

### 11.11.2 档位选择：不是"越大越好"

`model_server.find_gguf()` 原本只按量化档位排序（Q8_0 > Q6_K > …），
于是**装了 4B 之后仍然会继续用 2B**（因为 2B 是 Q8_0，量化更好）。
改成**先按参数量档位、再按量化**，并把偏好顺序写死成 `("4b", "2b", "9b")`：

| 档位 | 取舍依据 |
|---|---|
| **4B（首选）** | JevBench v1.4 hard tier **0.784**，校准 ECE **0.054**，是效果最好的档 |
| 2B（退路） | 只有 2.01 GB、最快，但区分度实测明显不足 |
| 9B（最后） | 公开题上**反而不如 4B**（hard tier 0.730）、校准更差（ECE 0.126） |

即"参数量越大越好"在这里是错的，因此刻意不用文件大小排序。

### 11.11.3 校准温度必须认版本号

新增 `model_server.size_key()`（从文件名解析 `4b-v0.2`）与
`provider.resolve_temperature_key()`（先试完整键、再退到主键）。
`advisor_from_args()` 在没显式给 `--model-size` 时**从实际会被加载的 GGUF 反推档位**。

⚠️ 4B 的 v0.2 与 v0.3 校准温度不同（**1.532 vs 1.367**）。认错版本的后果是概率
整体偏平 —— 而"概率偏平"恰恰是 2B 档最被诟病的地方，很容易被误判成"模型不行"。

### 11.11.4 实测对比（同一盘面 `Power.log --until-line 92000`）

### 11.12.2 大神打法的调研结论（外部内容，仅作规则依据）

来源：[水神Waterloo（2022 酒馆战棋世界冠军）升本节奏详解](https://news.17173.com/content/05192026/212644717.shtml)；
esports.gg 与知乎源均 403 不可读。**以下为外部网页内容，不是本项目产出的实测数据。**

五条定理：

1. **永远不要买弱随从，不如升本。**
2. **永远考虑你的下一回合行动** —— 要算两回合的费用衔接。
3. **君升我不升，君不升我升** —— 看对手战力做反节奏。
4. **切勿在不该升本时大代价贸然升本。**
5. **该升本时需果断，切记畏首畏尾。**

升降曲线（高度公式化）：**常规四费升二本约占 75% 对局**（最主流）；五费升二本
约 20%；六费升二本（特定英雄）；七费升二本直接到三本（Shinese Curve，古早）；
**五费升三本**是激进线（下限极低，567 费持续掉血）；**六费升三本**均衡。
原文原话：**「如果你不确定上不上，请上本。四费上二本一般都没有错。」**

### 11.12.3 真机审计：旧逻辑 6 次升本决策里 4 次与真人相反

对 `Hearthstone_2026_10_10_21_11_09/Power.log` 第一局（真人整局曲线
2本@T3、3本@T7、4本@T13、5本@T15，T20 血 10 阵亡）：

| 回合 | 满金 | 真人实际 | 旧引擎 |
|---|---|---|---|
| 3 | 4 | **1本→2本** | **不升** ❌ |
| 7 | 6 | 2本→3本 | 升本 ✅ |
| 9 | 11 | 不动 | **升本** ❌（早 2 回合） |
| 11 | 8 | 不动 | **升本** ❌ |
| 13 | 9 | 3本→4本 | 升本 ✅ |
| 15 | 10 | 4本→5本 | **不升** ❌ |

最严重一处的日志证据（`Power.log` 第 9974 行）：

```
TAG_CHANGE Entity=测试玩家#1234 tag=RESOURCES value=4
TAG_CHANGE Entity=测试玩家#1234 tag=RESOURCES_USED value=0
TAG_CHANGE ... tag=RESOURCES_USED value=4
... cardId=TB_BaconShopTechUp02_Button player=6] tag=COST value=4

```

即**金币 4、升本费 4、付 4、升到 2 本** —— 正是"四费升二本"。旧引擎判"不升"的
两个根因：① 采样时按钮 `COST` 还是**打折前的 5**，判成买不起；② 买不起直接
`-12` 分，压过了"1 本早升收益大 +6"。

### 11.12.4 实现

### 11.14 买牌阈值校准：结论是「阈值没用，分数只该用来排序」

症状：决策框几乎从不说「买」。旧规则要求 `score >= 18.0` 才输出「买」，而真机上
绝大多数店根本达不到这个分。

**方法**：新建 `tools/calibrate_shop.py` —— 用 5 份真机日志拍商店快照并打分，再和
真人**实际买了什么**对齐。买牌信号判定：商店槽位实体 `tag=2442` 指向的随从实体
`ZONE` 变成 `HAND` 且此刻 `CONTROLLER == 本地玩家`（刷新则是 `ZONE=REMOVEDFROMGAME`）。
必须**先筛事件再读 state**，否则每份日志要跑好几小时。

**实测（90 个商店快照 / 74 次购买）**：

| 判据 | 说「买」的店 | 精确率 | 召回率 |
|---|---|---|---|
| 旧：店内最高分 ≥ 18 | 24/90 | 92% | **29%** |
| 旧：店内最高分 ≥ 11 | 55/90 | 87% | 64% |
| **新：店内排名派发** | 63/90 | **92%** | **77%** |

（真人买牌店占比的基础率 = 33%。）

两条决定性的负面结论：

1. **分数对"买不买"没有预测力**。用「店内最高分」预测"这回合会不会买"的精确率，
   在 0~24 分的**每一个阈值上都贴着基础率 84% 不动**；而且"买了的店"和"没买的店"
   的最高分分位数很接近（p50 11.7 vs 17.0——没买的店反而更高，因为那正是场面满、
   无事可做的店）。所以**调阈值是死路**。
2. **但分数排序有效**。真人买走的那张牌，店内排名第 1 占 **47.1%**、前 2 占 **66.7%**
   （纯随机约 30%）；中局（5-9 回合）第 1 名命中 **64.7%**。而且店内第 1 名的买入率
   按分数段看相当平：4-7 分 **91.7%**、7-10 分 100%、10-13 分 94.4%、13-16 分 69.2%、
   16-19 分 75%、19-22 分 87.5%、22+ 分 71.4%。

**落地**（`src/hsbg/rules.py`）：新增 `RulesEngine._assign_shop_actions()`，动作不再由
绝对分数线给，而是**按店内排名**派发 ——

- 凑三连 → `买`（硬收益，不受排名限制）
- 第 1 名且 `score >= BUY_TOP_MIN`（**4.0**）→ `买`
- 第 2、3 名 → `考虑`；第 4 名及以后 → `跳过`
- 买不起 → `跳过`
- 场面已满（`>= cfg.board_limit`）→ 把第 1 名的 `买` 降级为 `考虑`，理由写「场面已满」

⚠️ 两个必须记住的坑：

1. **地板分只能压到 4 分**。实测最低的 4-7 分段买入率仍有 91.7%，一张 1 星 2/3 的裸
   随从就只值 4.5 分 —— 地板设成 6.0 会把大量真人真会买的牌判成「考虑」。
2. **免费刷新不能让位给「买」**。`_decision` 的分支顺序是「有牌可买 → 买」，免费刷新
   只在**没有可买 / 买不起**时才顶上来；有牌可买时买牌优先（免费刷新是买完之后顺手用的）。
   所以 `test_decision_asks_for_the_refresh_when_it_is_free` 的夹具用的是**空商店**。

验收（`./run-tests` 297 → **303** 通过；`./hsbg check` 11/11）：新增 6 项钉住排名派发，
并修正了 2 个因动作变了而失效的旧断言（`test_decision_asks_for_the_refresh_when_it_is_free`
的夹具、`test_empty_board_buys_a_body_instead_of_a_spell` 的 trigger 断言）。

## 11.15 饰品实证分：HSReplay 数据接进规则层（2026-10-15）

> 承接 §11.8.3 的"有意保守"：饰品不打分是因为**没有样本**，不是不想要。
> 这次找到了可复现的实证来源，把 P14 落地。

### 11.15.1 数据来源

`tools/fetch_hsreplay.py` 拉 HSReplay 公开端点（**无需 API key**，但要带 UA，
否则 403）：

```
https://hsreplay.net/api/v1/battlegrounds/trinkets/?BattlegroundsMMRPercentile=<ALL|TOP_1_PERCENT>
```

落盘 `data/trinkets_hsreplay.json`（带快照时间戳 `fetched_at`）：

| 字段 | 含义 |
|---|---|
| `brackets.ALL` / `brackets.TOP_1_PERCENT` | 分段（255 / 252 行） |
| `card_id` / `name` / `group` | CardID（靠 `data/cards_raw_zhCN.json` 的 dbfId 映射）/ 中文名 / lesser·greater |
| `tier` | HSReplay 的档位 `s/a/b/c/d/f` |
| `pick_rate` | 被 offer 后**被选走**的百分比 |
| `avg_final_placement` | 终局平均名次（越小越好，1 = 吃鸡） |
| `extra_data` | 极少条目才有：**大厅种族上下文**（见 11.15.3） |

### 11.15.2 打分公式（`src/hsbg/trinkets.py`）

```
score = TIER_BASE[tier] + (4.2 − avg_final_placement) × 3.0
TIER_BASE = {S: 3.0, A: 1.5, B: 0.5, C: −0.5, D: −1.5, F: −3.0}
```

标定依据（ALL 分段、聚合后 237 件，2026-10-15 快照）：

| tier | S | A | B | C | D | F |
|---|---|---|---|---|---|---|
| 平均名次中位数 | 3.53 | 3.94 | 4.14 | 4.33 | 4.44 | 4.78 |
| 件数 | 13 | 64 | 43 | 40 | 74 | 3 |

- 全体名次区间 3.18–4.85、中位数 **4.22** → 取 **4.2** 当参照点（= 0 分）。
- 名次项实际贡献 ±2.5 分，与 tier 的 ±3 分同量级 —— tier 给跨档粗排序，
  名次在同档内细分，两者不互相淹没。
- ⚠️ **固定用 `ALL`**：样本最大（255 行）。`TOP_1_PERCENT` 也能加载，但它的 tier
  口径不同（同一件饰品判 F 级的数量是 ALL 的 5 倍），**两套不能混用**。

### 11.15.3 数据里的两个坑

1. **同一 `card_id` 多行**：只有 2 件（`BG30_MagicItem_426` 多彩罗盘的小/大型），
   每件 10 行 —— HSReplay 把"这件饰品在不同大厅种族组合下的表现"分行给出
   （`extra_data` 是种族位）；其余 235 件都只有 1 行。
   **聚合成 1 行：取"平均名次的中位数行"**，并标 `race_context=True`
   （展示为"大厅种族相关"）。
   - 取最好 = 假设大厅种族正好是它的最佳组合（高估）；
   - 逐项平均 = tier 没有"平均档"可对应（展示层会说谎）；
   - 中位数 = "典型大厅"下的表现，标出来即可解释。

   ⚠️ 大厅的种族组合在日志里**读不到**，所以做不到按大厅精确取行。

## 11.16 复盘回放（P7）：每局落盘 + 离线回看（2026-10-16）

### 11.16.1 录制挂钩在哪

Swift 悬浮框跑的就是 `hsbg panel` 的跟随模式（`DataFeed.swift`），面板每
`--interval` 秒出一帧。录制器（`src/hsbg/replay.py` 的 `ReplayRecorder`）就挂在
这个帧循环上：**开着悬浮框打游戏 = 自动录像**，不需要任何额外命令。

一局一个文件：`replays/20261016-193952-瓦尔登·晨拥.json`（目录可用
`HSBG_REPLAY_DIR` 或 `--replay-dir` 覆盖；已在 `.gitignore` 里）。

### 11.16.2 三个设计决策（都是踩过才这么写的）

- **新局判据 = 回合回卷**：`StateBuilder` 在新号 `CREATE_GAME` 时重建 `GameState`，
  下一帧 `turn` 从 12 → 1 回卷。⚠️ 判断必须发生在"更新内部记忆"**之前** ——
  新局的空 `choice_log` 不能盖掉正要落盘的旧局数据。
- **周期落盘（15s）+ 原子重写**：悬浮框是长期进程，App 退出走 SIGTERM，
  Python 的 `finally` **不会执行**。只在局终/退出写盘的话，中途被杀 = 整局白录。
  实测冒烟：强杀进程后，磁盘上仍有最近一次 checkpoint 的完整 JSON。
- **帧去重**：面板每 0.4s 无条件出帧，绝大多数帧与上一帧逐字节相同；按整帧
  JSON 去重，不然一局能写十几 MB。`partial`（是否录到收尾）写进文件头。

## 11.17 英雄选择实证分（S1）：开局三选一接 HSReplay（2026-10-16）

> 场景 S1：开局三选一。原以为日志里拿不到"候选是谁"，实测**拿得到** ——
> 而且和饰品一样有可复现的实证来源（虽然只剩"选取率 + 护甲"，见下），
> 于是把规则层接上。

### 11.17.1 数据来源：只有"选取率 + 护甲"

`tools/fetch_hsreplay.py --heroes` 拉免费端点（路径里的 `/free/` 是必须的，
完整版 `/heroes/` 要登录；平均名次与 tier 是 Tier7 订阅内容，公开渠道拿不到）：

```
https://hsreplay.net/api/v1/battlegrounds/heroes/free/?BattlegroundsMMRPercentile=<ALL|TOP_50_PERCENT|TOP_1_PERCENT>&BattlegroundsTimeRange=LAST_7_DAYS
```

落盘 `data/heroes_hsreplay.json`：

| 字段 | 含义 |
|---|---|
| `brackets.ALL` / `TOP_50_PERCENT` / `TOP_1_PERCENT` | 分段（116 / 116 / 92 行，2026-10-16 快照） |
| `card_id` / `name` | CardID（dbfId 映射；与日志里的候选卡号一致，116/116 全对得上）/ 中文名 |
| `pick_rate` | 被 offer 后**被选走**的百分比 |
| `armor` | 起始护甲（**只展示，不参与打分**） |

⚠️ 时间窗只有 `LAST_7_DAYS` 可用（`PATCH` / `LAST_30_DAYS` 实测 400）。

### 11.17.2 打分公式（`src/hsbg/heroes.py`）

```
score = 10 × 选取率在全体英雄里的百分位
```

- **为什么用选取率**：免费层唯一可得的实证数值。选取率 = 玩家群体对英雄强度的
  **共识代理**（实测 ALL / TOP 50% / TOP 1% 三个分段排序高度一致），同一补丁内
  稳定可比。
- **为什么护甲不参与打分**：护甲是暴雪的平衡杠杆 —— 弱英雄补甲（实测选取率
  8% 的英雄有 14 甲），高低**不单调**对应强弱，只放进展示行供人参考。
- 分数只用在一局内几个候选之间的相对排序，**不跨补丁比较**。

### 11.17.3 日志侧的三个坑（实测才发现的）

1. **英雄选择在日志里叫 `MULLIGAN`**：头行是
   `GameState.DebugPrintEntityChoices() … ChoiceType=MULLIGAN`，选项行
   `Entities[i]=[… cardId=BG22_HERO_004 …]`（`Source=GameEntity`，实测 4 个候选）。
   与普通起手换牌同类型 —— 靠**选项卡号带 `_HERO`** 区分（实测三份会话一致）。
2. **选择时本地身份还没认出来**：`CURRENT_PLAYER` 切到本地玩家要等选完英雄
   （实测约 30–50 s 后），而三选一在开局约 0.6 s 就弹了；`state` 里按账号名
   比对的 `is_local` 会判 False → 英雄块整个不显示。退路：**选项实体全部归
   本地座位**（`CONTROLLER` = 本地玩家 id —— 来自 CREATE_GAME 里带真实
   `GameAccountId` 的玩家实体）→ 认作自己的选择。两条路都不成立才返回 False
   （宁可漏报也不误报）。
3. **决策框的兜底顺序**：`BEGIN_MULLIGAN` 不在招募期、座位也还没建 ——
   英雄选择必须先于"还没有本地玩家信息 / 战斗阶段"两个兜底处理，
   否则决策框会说"战斗阶段，等结算"。
